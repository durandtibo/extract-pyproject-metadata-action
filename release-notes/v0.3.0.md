# v0.3.0

`v0.3.0` is a breaking release compared with `v0.2`. `v0.2` had the inputs `pyproject-path`
and `extra-values` and the outputs `name`, `version` and `extras`. This release keeps them,
makes their behaviour stricter, and adds what a workflow needs to build, test and install
a project from its `pyproject.toml`.

## Pin

Pin the exact tag: `uses: durandtibo/extract-pyproject-metadata-action@v0.3.0`. No `v0.3`
tag is moved to a later release: a tag never changes after it is published.

## New inputs

| Input               | Purpose                                                                                                                      |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `dependencies`      | A JSON array of the packages whose specifier to read (`numpy`, `pytest@group:dev`, `tqdm@extra:cli`); a name that is not a valid package name is an error.                        |
| `python-candidates` | A JSON array of the `major.minor` Python versions (`3.12`, not `03.12`) to choose from; `""` is the default list (the README shows it).            |
| `strict`            | `"true"` fails on any warning (a dynamic version, a dependency that is not found, ...); `"false"` (default) only reports it. |

`pyproject-path` and `extra-values` are unchanged.

## New outputs

13 outputs in all. The 3 of `v0.2` are `name`, `version` and `extras`; the 10 new ones are:

| Output                  | Purpose                                                                                            |
| ----------------------- | -------------------------------------------------------------------------------------------------- |
| `normalized-name`       | The name normalized per PEP 503 (`my-package`), for an index and `pip install`.                    |
| `file-name`             | The name as it is written in the file names of wheels and sdists (`my_package`).                   |
| `normalized-version`    | The version in the canonical form of PEP 440.                                                      |
| `requires-python`       | `[project].requires-python`, as declared.                                                          |
| `python-versions`       | The candidates that `requires-python` allows, for a test matrix.                                   |
| `python-min`            | The lowest of the `python-versions`.                                                               |
| `python-max`            | The highest of the `python-versions`.                                                              |
| `groups`                | The names of the dependency groups of `[dependency-groups]`.                                       |
| `dependency-specifiers` | The specifier of each package requested with `dependencies` (`null` if it is not found).           |
| `json`                  | All the values, the requirements with their markers and the warnings, as real JSON, in one output. |

## Changed behaviour

- `extras` are normalized (PEP 685), without duplicates, and sorted.
- Every error is `<field>: <problem>` (`[project].version: not a valid PEP 440 version: '1.x'`,
  `strict: must be 'true' or 'false', got: 'yes'`, `pyproject-path: not a file`), reported as an
  `::error` annotation on the file.
- A suspicious but usable input is a `::warning` annotation with a stable code
  (`dependency-not-found`, `dynamic-version`, ...; the table is in the README), and is in
  the `warnings` array of `json` as `{"code", "message"}`. `strict` turns every warning into
  a failure.
- The `json` output has `schema_version` `1`. It increases only when a key is renamed, removed or changes type.
- The fields that no output needs are neither read nor validated. The requirement tables
  (`dependencies`, `optional-dependencies`, `dependency-groups`) are read only when the
  `dependencies` input is not empty.
- The program that the action starts has no command line: it reads the inputs from
  `INPUT_PYPROJECT_PATH`, `INPUT_EXTRA_VALUES`, `INPUT_DEPENDENCIES`, `INPUT_PYTHON_CANDIDATES`
  and `INPUT_STRICT`, and prints the JSON when `GITHUB_OUTPUT` is not set.

## Platforms

Linux and macOS runners are supported. Windows is not supported. The action needs Python 3.11
or later on `PATH`; nothing is installed or downloaded.

## What the action does not do

- It never runs project code or a build backend.
- It does not resolve a dynamic version: it reports it (`dynamic-version`). Ask the build
  backend (`python -m build`, `hatch version`) for the value.
- It does not evaluate environment markers: the first matching requirement wins.
